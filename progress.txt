## Architecture and invariants
The Vercel proxy is mandatory: host-only Secure/HttpOnly SameSite=Lax session/CSRF cookies must remain same-origin. Never point browser API calls directly at Render. Nginx is local-Docker-only. Backend: Java 21, Spring Boot 3.5.14, Security/JPA/PostgreSQL. Frontend: React 18, TypeScript, Vite 6, TanStack Query.

Auth is custom app auth, not Supabase Auth. Accounts are in `app.app_users`; browsers never connect to Supabase. User IDs `[A-Za-z0-9_.-]{3,32}`, lowercase-normalized; passwords 12–72 UTF-8 bytes, BCrypt 12. Random 32-byte sessions store SHA-256 hashes, expire after 12h, revoke on logout. CSRF stays enabled. DB throttling survives restarts. Render requires proxy secret/client IP. Tasks are owner-scoped; foreign tasks return not found; mutations use optimistic versions. No password recovery exists.

Frontend retries cold starts, offers retry, deduplicates CSRF, retries auth once after stale verification, uses 15s timeout, aborts on account change, syncs tabs. Key files: `src/main/java/com/taskflow/security/`, `AuthGate.tsx`, `http.ts`.

CRITICAL - DEPLOYMENT BLOCKERS

1. Vercel cannot currently reach the backend.

   Evidence:
   - frontend/src/app/api/http.ts:1 defaults requests to /api/v1.
   - frontend/.env.example also specifies /api/v1.
   - No vercel.json, Vercel function, or committed external rewrite exists.
   - frontend/nginx.conf contains a proxy, but Vercel static hosting does not run it.

   Impact:
   Authentication and task requests deployed on Vercel return 404.

   Recommended fix:
   Add a Vercel external rewrite or same-origin proxy from /api/* to the public
   Render backend.

2. An absolute Render API URL breaks the current cookie model.

   Evidence:
   - AuthController.java:54-56 creates a host-only SameSite=Lax session cookie.
   - SecurityConfig.java:19-20 creates a SameSite=Lax CSRF cookie.
   - Vercel and Render domains are cross-site.

   Impact:
   Login may appear successful, but browsers will not reliably send the session and
   CSRF cookies from the Vercel page to Render. Subsequent calls return 401 or 403.

   Recommended fix:
   Keep browser API calls on the Vercel origin and proxy /api through Vercel. Do not
   rely only on CORS or credentials: include.


HIGH-PRIORITY PROBLEMS

3. Signed-in UI is effectively unusable on mobile.

   Evidence:
   - frontend/src/app/App.tsx:161-172 uses a fixed horizontal layout and hides overflow.
   - frontend/src/app/components/LeftPanel.tsx:82-84 reserves a non-shrinking 320px sidebar.

   Impact:
   At 320-375px viewport widths, the task panel is clipped or inaccessible.

   Recommended fix:
   Move the sidebar into a mobile drawer, add responsive layout breakpoints, and
   collapse topbar labels and controls on small screens.

4. Optimistic-lock conflicts trap the open edit/delete modal on a stale version.

   Evidence:
   - frontend/src/app/App.tsx:110-139 continues using editingTask.version after a 409.
   - Query invalidation does not replace the editingTask snapshot used by the modal.

   Impact:
   Every retry fails until the user closes and reopens the task.

   Recommended fix:
   On 409, fetch the latest task and refresh the modal version, or close the modal
   with a clear conflict-resolution message.

5. Render cold starts are not handled.

   Evidence:
   - frontend/src/app/auth/AuthGate.tsx:23-30 attempts authApi.me() once.
   - The React Query retry policy does not cover this direct startup request.

   Impact:
   A transient Render wake-up error sends a valid user to the login screen with no
   automatic recovery.

   Recommended fix:
   Add a server-starting state, bounded exponential retry, cancellation, and a manual
   retry action before deciding that session restoration failed.

6. Proxy-hosted authentication can place unrelated users in one throttle bucket.

   Evidence:
   - AuthController.java:32 and 39 use req.getRemoteAddr().
   - Forwarded-header processing exists only in application-docker.properties:6.
   - The Supabase/Render profile does not enable trusted forwarded-header processing.

   Impact:
   Vercel/Render proxy addresses may become shared throttle keys. A small number of
   failures could temporarily block registration or login for every visitor.

   Recommended fix:
   Configure and verify trusted forwarded-header processing for the actual production
   ingress, and enforce primary rate limits at a trusted edge or shared store.

7. The selected timezone affects only the topbar clock.

   Evidence:
   - frontend/src/app/App.tsx:28 stores the selected timezone.
   - frontend/src/app/api/http.ts:62 always sends the browser system timezone.
   - Calendar/date rendering also uses browser-local Date behavior.

   Impact:
   Changing the timezone does not change Today, Tomorrow, calendar boundaries, task
   display, or statistics.

   Recommended fix:
   Introduce one application-timezone source used by API headers, query keys, calendar
   calculations, editing, and display. Alternatively, label this as clock-only.

8. Unlimited task creation and an unbounded calendar response permit resource abuse.

   Evidence:
   - TaskController.java:80-82 allows task creation without a user quota/rate limit.
   - TaskCreateDTO.java:12-13 permits 10,000-character descriptions.
   - TaskController.java:68-72 returns every task in a month as one List.

   Impact:
   A registered account can exhaust Supabase quotas and create expensive responses or
   backend memory pressure.

   Recommended fix:
   Add per-user creation/storage quotas, ingress rate limits, and pagination or a hard
   result cap for calendar data.

9. The backend does not follow the dynamic PaaS port contract.

   Evidence:
   - src/main/resources/application.properties:2 hardcodes server.port=8081.

   Impact:
   Render/Railway health routing can fail or require fragile manual port configuration.

   Recommended fix:
   Use server.port=${PORT:8081}.


INDEXEDDB AND LOCAL-CACHE PROBLEMS

10. A stale GET can repopulate the cache after a mutation clears it.

    Evidence:
    - frontend/src/app/api/http.ts:81-83 schedules successful GET cache writes without
      awaiting them or tying them to a cache mutation generation.

    Impact:
    A pre-mutation response that completes late can remain cached for up to 24 hours.

    Recommended fix:
    Track a per-user cache generation. Increment it before mutations and reject writes
    created under an older generation.

11. Expired records can remain physically stored indefinitely.

    Evidence:
    - frontend/src/app/cache/localCache.ts:93-115 deletes an expired entry only when
      that exact key is read.
    - Pruning is otherwise triggered only after another write for the same owner.

    Impact:
    Logically expired task data can remain in IndexedDB on shared devices.

    Recommended fix:
    Sweep expired records when the database opens, when users authenticate, and at
    bounded maintenance intervals.

12. Cache deletion failures are reported as successful.

    Evidence:
    - localCache.ts:57-60 swallows all queued IndexedDB errors.
    - setLocalCacheEnabled(false) consequently returns success after a failed clear.
    - App.tsx:40-50 displays LOCAL DATA CLEARED.

    Impact:
    Users can be falsely told that local task data was removed.

    Recommended fix:
    Propagate deletion failures separately from best-effort cache-write failures and
    show success only after the deletion transaction completes.

13. Network requests have no timeout before cache fallback.

    Evidence:
    - frontend/src/app/api/http.ts:63 uses fetch without a bounded timeout.

    Impact:
    A stalled request can display loading indefinitely and never return cached data.

    Recommended fix:
    Combine caller cancellation with an internal timeout and preserve a distinct
    timeout/network error classification.

14. Cached fallback data is indistinguishable from live data.

    Impact:
    Users can act on stale task data without knowing the server is unavailable.

    Recommended fix:
    Return freshness metadata from the request/cache layer and display an offline or
    stale-data banner.


DATA, STATISTICS, AND FILTERING PROBLEMS

15. Sidebar statistics do not match the corresponding filters.

    Evidence:
    - LeftPanel.tsx:198-214 displays remaining-task counts for Today, Tomorrow, and
      This Week.
    - TaskSpecifications.java:51-55 applies only date ranges for those quick filters,
      so completed/cancelled tasks are also returned.

    Impact:
    A label can show one task, while clicking it displays several.

    Recommended fix:
    Apply remaining() to those filters or change the displayed totals to count the
    same data returned by each filter.

16. completedToday does not mean completed today.

    Evidence:
    - TaskService.java:47-48 counts completed/cancelled tasks due today.
    - Task.java has no completedAt timestamp.

    Impact:
    A task completed today but due tomorrow is excluded; a task completed yesterday
    but due today is included.

    Recommended fix:
    Persist completedAt on status transitions and define separately whether CANCELLED
    should count as completed.

17. Lower-bound date filtering unexpectedly includes undated tasks.

    Evidence:
    - TaskSpecifications.java:41-43 implements startDate as dueAt >= startDate OR
      dueAt IS NULL.

    Impact:
    General date-range searches include tasks that do not have a date. The main
    timeline currently relies on this undocumented behavior.

    Recommended fix:
    Make undated inclusion an explicit request option instead of part of startDate.

18. Due-state styling disagrees with backend overdue behavior.

    Evidence:
    - TaskCard.tsx:38-54 compares calendar days instead of the exact due instant and
      does not neutralize completed/cancelled tasks.

    Impact:
    A task due earlier today is styled as Today while the backend calls it overdue.
    Completed historical tasks can retain a red overdue accent.

    Recommended fix:
    Compare active tasks with the exact current instant and style terminal states
    independently.

19. Custom categories entered in TaskModal are not reusable.

    Evidence:
    - TaskModal.tsx:178-180 includes custom text only in the current request.
    - The category is not added to App.customCategories.

    Impact:
    It cannot be selected normally for the next task or used from the sidebar filter.

    Recommended fix:
    Persist categories server-side, derive them from tasks, or append successful new
    categories to the opted-in local preferences.


UX AND ACCESSIBILITY PROBLEMS

20. Calendar/statistics failures are silently shown as empty data or zero counts.

21. Primary workflows have accessibility failures.

    Impact:
    React Query state, local task cache, and an unsaved task draft can be cleared.

    Include account/session identity in broadcasts and avoid resetting same-account

23. Task mutations are not broadcast to other tabs.

    Impact:
    Another foreground tab can retain stale tasks until an unrelated refetch occurs.

    Recommended fix:
    Broadcast per-user task invalidation events after successful mutations.

24. Stored preferences are trusted without validation.

    Evidence:
    - localCache.ts:80-85 parses and returns arbitrary stored JSON.
    - There is no application error boundary.

    Impact:
    Corrupt or manually edited preferences can crash authenticated rendering.

25. Public-page metadata is unfinished.

    Evidence:
    - frontend/index.html contains PC version adaptation text and noindex, nofollow.

    Impact:
    A public deployment is intentionally excluded from search indexing and has an

BACKEND AND SECURITY HARDENING

26. Secure cookies depend on an easy-to-miss environment variable.

    Evidence:
    - AuthController.java and SecurityConfig.java default app.cookie-secure to false.
    - application-supabase.properties does not override the default.

    Recommended fix:
    Make secure cookies the production/Supabase default and require an explicit local
    development override.

27. Authentication throttling is instance-local and restart-sensitive.

    Evidence:
    - AuthThrottle.java stores windows in an in-memory LinkedHashMap.

    Impact:
    Render cold starts/restarts clear limits, and multiple replicas enforce unrelated
    limits. A synchronized full-map expiry scan also occurs on every attempt.

    Recommended fix:
    Use a trusted ingress limiter or a shared bounded rate-limit store.

28. Authenticated requests and statistics use excessive database round trips.

    Evidence:
    - AuthService.java:57-60 performs a session lookup followed by a user lookup on
      every authenticated request.
    - TaskService.java:45-50 executes six separate statistics queries.
    - The Supabase Hikari pool defaults to five connections.

    Recommended fix:
    Query session identity with one join/projection and compute statistics with one
    conditional-aggregation query.

29. The documented Supabase database identity is overprivileged.

    Evidence:
    - .env.supabase.example and docs/supabase.md use postgres.PROJECT_REF.

    Impact:
    Backend credential compromise has a larger database blast radius than necessary.

    Recommended fix:
    Create a dedicated least-privilege application role with only the required
    schema/table/sequence permissions.

30. Database permits ownerless tasks.

    Evidence:
    - The ownership migration adds nullable user_id.
    - Task.userId lacks nullable=false.

    Impact:
    Future application bugs or manual writes can create inaccessible orphan rows.

    Recommended fix:
    Resolve legacy rows and then make user_id NOT NULL.

31. Validation error handling is brittle for object-level constraints.

    Evidence:
    - GlobalExceptionHandler.java:57-60 casts every validation error to FieldError.

    Impact:
    A future record/class-level validator can turn a normal 400 into a 500.

    Recommended fix:
    Handle FieldError and ObjectError separately.

38. Production observability is minimal.
