## 3. Architecture decisions that must be preserved

The Vercel same-origin proxy is required. The application uses host-only Secure/HttpOnly SameSite=Lax session cookies plus CSRF cookies. Sending browser API requests directly from Vercel to Render would make them cross-site and break or weaken the current cookie model. Browser calls must remain at `/api/v1` on the Vercel origin.

Nginx is not used in Vercel production. It is used only in the local Docker frontend container to serve the Vite build and proxy `/api` to the backend.

Technology stack:

- Backend: Java 21, Spring Boot 3.5.14, Spring MVC, Spring Security, Spring Data JPA, Jakarta Validation, PostgreSQL, HikariCP, Maven.
- Frontend: React 18.3.1, TypeScript, Vite 6.3.5, TanStack React Query 5, Tailwind CSS 4, Radix/shadcn-style components, Vitest.
- Testing: JUnit/Spring Boot Test/Testcontainers PostgreSQL and Vitest/fake-indexeddb.
- Production: Vercel + Render free Docker web service + Supabase PostgreSQL.
- Local: Docker Compose PostgreSQL + migration job + backend + Nginx frontend.

## 4. Authentication and authorization

Taskflow uses custom application authentication, not Supabase Auth. Accounts live in `app.app_users`; the browser never connects directly to Supabase and receives no database credentials.

Rules and controls:

- User ID regex: `[A-Za-z0-9_.-]{3,32}`.
- User IDs normalize to lowercase.
- Passwords are 12–72 UTF-8 bytes; registration requires confirmation.
- Passwords use BCrypt strength 12 and are never stored plaintext.
- Unknown-user login performs a dummy BCrypt check to reduce timing leakage.
- Sessions use 32 random bytes; the database stores only SHA-256 token hashes.
- Sessions expire after 12 hours and are revoked on logout.
- Cookie: `TASKFLOW_SESSION`, HttpOnly, Secure in production, SameSite=Lax, path `/`.
- CSRF remains enabled; mutations use `X-XSRF-TOKEN` obtained from `GET /api/v1/auth/csrf`.
- Spring Security is stateless; `SessionFilter` establishes custom identity.
- Login/registration throttling uses shared PostgreSQL rows and survives backend restarts.
- Render mode requires the Vercel proxy secret and trusted client IP header.
- Every task query and mutation is scoped to the authenticated user.
- Foreign tasks return not found rather than revealing existence or ownership.
- Updates, status changes, and deletes require optimistic versions.
- There is currently no email address or password-recovery flow.

Frontend auth behavior:

- Restores the session through `/auth/me`.
- Retries Render cold starts up to five times with bounded backoff.
- Offers manual retry if the backend remains unavailable.
- Uses a 15-second API timeout.
- Deduplicates CSRF requests.
- Retries authentication once after stale verification/CSRF failure.
- Aborts pending requests after account changes.
- Synchronizes login, logout, session expiry, and task mutations across tabs.
- Clears React Query and browser cache state when account identity changes.
- Checks `X-Taskflow-User` to detect an unexpected session/account switch.

Important files:

- `src/main/java/com/taskflow/security/`
- `frontend/src/app/auth/AuthGate.tsx`

## 6. Supabase/PostgreSQL design

Supabase is managed PostgreSQL only; application authentication and authorization remain in Spring.

Committed migrations:

1. `supabase/migrations/20260913143000_create_taskflow_schema.sql`
2. `supabase/migrations/20260913160000_add_accounts_and_ownership.sql`
3. `supabase/migrations/20260915120000_harden_runtime.sql`

Private schema `app` contains:

- `app.app_users`: normalized user IDs and BCrypt hashes.
- `app.tasks`: user-owned tasks.
- `app.login_sessions`: hashed session tokens and expirations.
- `app.auth_rate_limits`: shared throttle windows.
- `app.schema_version`: deployment compatibility gate.

Database controls:

- Required application schema version: 3.
- Supabase profile uses Hibernate `ddl-auto=validate`; migrations own production schema changes.
- RLS is enabled as defense in depth.
- `anon`, `authenticated`, and `PUBLIC` browser roles have no application-table access.
- Intended backend role `taskflow_app` has required schema/table/sequence privileges only, with no superuser, role creation, database creation, or RLS bypass.
- Use Supabase Session pooler/direct connection on port 5432. Do not use transaction pooler port 6543 with Hibernate.
- Pooler username is generally `taskflow_app.<project-ref>`; use the exact Supabase Connect value.
- Create normal test users/tasks through the application API, never direct SQL, so hashing, CSRF, ownership, quota, and audit paths are exercised.

Relevant files: `docs/supabase.md`, `.env.supabase.example`, `supabase/config.toml`, `application-supabase.properties`, and `SchemaHealth.java`.

## 7. Per-user browser cache

The cache is optional and local to the user's browser/device. It does not consume Render disk or create cache rows in Supabase.

- Opt-in control: account menu -> “Save on this device”.
- IndexedDB database: `taskflow-local-cache-v1`.
- localStorage stores consent and validated UI preferences.
- IndexedDB stores successful task GET responses only.
- Scope includes browser origin, API root, and authenticated user ID.
- Passwords, cookies, CSRF tokens, session tokens, and offline mutations are never cached.
- Network-first behavior; cached fallback is visibly marked stale.
- TTL: 24 hours.
- Limit: 80 records and approximately 4 MiB per user.
- Expired-record sweep and least-recently-touched pruning.
- Serialized writes and cross-tab task invalidation.
- Revision/epoch fencing prevents late stale GETs from repopulating data after mutation, logout, or clear.
- Disabling consent clears that user's cached records and preferences.
- Browser policy, private browsing, or storage pressure may evict IndexedDB.
- This is a read cache, not offline synchronization; task writes require the server.

Files: `frontend/src/app/cache/localCache.ts`, `preferences.ts`, `localCache.test.ts`, `http.ts`, and `Topbar.tsx`.

## 15. Troubleshooting map

Account creation/login:

- 404: Vercel rewrite or catch-all regression.
- Browser “decoding failed”: proxy forwarded stale encoding/length headers.
- `403 Invalid CORS request`: exact active Vercel origin missing from Render CORS.
- Other 403: stale CSRF, proxy-secret mismatch, or direct Render access.
- 502: Render waking or unreachable.
- 503 from proxy: backend URL/secret missing or secret too short.
- 401 after successful login: inspect Vercel `Set-Cookie` forwarding and cookie attributes; do not bypass the proxy.

Backend not ready:

- Inspect Render logs for connection, credential, Hibernate validation, or schema-version errors.
- Ensure JDBC URL has one `jdbc:postgresql://` prefix and correct database/SSL parameters.
- Use Session pooler 5432, not transaction pooler 6543.
- Confirm username format and rotated password.
- Confirm all three migrations and schema version 3.
- Confirm `supabase,render` profiles and required environment variables.

Frontend deployment:

- Confirm Vercel root directory `frontend`.
- Run `npm ci`, `npm test`, and `npm run build` locally.
- Confirm `vercel.json` and catch-all function are deployed.
- Confirm both production Vercel variables exist.

Cache:

- Confirm consent for the current user.
- Inspect IndexedDB `taskflow-local-cache-v1` and scoped localStorage keys.
- Remember private browsing/storage pressure may evict data.
- Disabling cache must remove the current user's records/preferences.
- Cached data cannot create offline tasks.
